# BUZZ Pro — دليل نقل المشروع لإعادة الهيكلة (لـClaude Code)

## ما هو هذا المشروع

**BUZZ Pro** تطبيق SaaS مالي متعدد المستأجرين (Multi-Tenant) لإدارة محلات صغيرة بالأردن (مقاهٍ، مطاعم) —
إيرادات، مصاريف، رواتب وحضور موظفين، جرد نقدي، تسوية بنكية، فواتير ذكية بالذكاء الاصطناعي، وإشعارات فورية.

- **الواجهة**: React (ملف واحد ضخم حاليًا — هذا بالضبط ما نريد إصلاحه)
- **الاستضافة**: Netlify (`glistening-pasca-79bbb0.netlify.app`)
- **الخلفية**: Supabase (المشروع: `nhfemosbdsyzhrfjpjsb`) — قاعدة بيانات Postgres + مصادقة + Edge Functions (Deno)
- **الذكاء الاصطناعي**: Claude API (نص + رؤية للفواتير) عبر Supabase Edge Functions
- **إشعارات الدفع**: Web Push (VAPID) عبر Service Worker

## ⚠️ المشكلة التي يجب حلّها (سبب هذا النقل)

الملف `source/app-current-monolith.jsx` هو **الكود الفعلي العامل بالإنتاج حاليًا**، لكنه:
1. **ملف واحد** بأكثر من ٥٠٠٠ سطر أصليًا (توسّع لأكثر من ٨٠ ألف سطر بعد إعادة التنسيق من نسخة مُصغَّرة).
2. **أسماء المتغيّرات مُختصَرة تلقائيًا** (مثل `e`, `t`, `Bt`, `ye`) — نتيجة تصغير (minification) متكرّر، **ليس** الكود الأصلي الذي كُتب به.
3. لا فصل بين المكوّنات (كل شيء بملف واحد: الداشبورد، الإيرادات، المصاريف، الموظفين، الرواتب، الجرد، تسوية البنك...).

**هذا الملف يعمل بشكل صحيح ١٠٠٪ بالإنتاج حاليًا** (اختُبر بعمق طوال جلسة تطوير طويلة جدًا) — **المطلوب: إعادة هيكلته لبنية ملفات نظيفة ومنطقية، مع الحفاظ على كل المنطق التجاري والحسابات المالية بلا أي تغيير في السلوك.**

## الأولوية القصوى: لا تكسر الحسابات المالية

هذا التطبيق يُستخدَم فعليًا بمحل قهوة حقيقي (BUZZ Coffee) يعتمد عليه صاحبه يوميًا. **أي إعادة هيكلة يجب أن تحافظ بدقة متناهية على**:
- معادلة حساب الرواتب (`computeAttendancePayroll` بالكود الحالي) — تتضمّن: نسبة الساعات، الساعات الإضافية بمعدَّل مختلف، "منحة ثقة" قبل تفعيل البصمة، ربط تاريخ التوظيف بحدود الحساب.
- معادلة الجرد النقدي (`computeAll`) — التوازن بين الخزنة والبنك، حركات الأموال، المطابقة.
- كل الصيغ بالدولار/الدينار (٣ خانات عشرية، عرض الأرقام السالبة بعلامة "−" صريحة داخل قوسين).

**التوصية:** ابدأ بفهم `computeAll` و`computeAttendancePayroll` بعمق، اكتب اختبارات (tests) عليهما أولًا **قبل** أي إعادة هيكلة، للتأكد من عدم كسر أي رقم.

## بنية المجلدات بهذه الحزمة

```
source/
  app-current-monolith.jsx     ← الكود الحالي الكامل (نقطة البداية المرجعية)
database/
  migrations/                  ← كل ترقيات SQL بالترتيب التاريخي (شغّلها بالترتيب لو أعددت قاعدة بيانات جديدة للاختبار)
  edge-functions/              ← كل دوال Supabase Edge Functions المنشورة فعليًا
```

## الميزات الفعلية المبنية (للتأكد من عدم فقدان أي منها أثناء إعادة الهيكلة)

- محاسبة يومية: إيرادات، مصاريف (بفئات وتصنيفات فرعية مخصَّصة لكل منشأة)، تكاليف ثابتة، حركة أموال
- **فواتير ذكية**: تصوير فاتورة → قراءة بالذكاء الاصطناعي (رؤية) → كشف هل هي فاتورة حقيقية → تصنيف كل صنف بفئته الخاصة → تنبيه ارتفاع الأسعار → تقرير أسعار المواد بمرور الزمن
- جرد نقدي يومي ومطابقة (خزنة/بنك)، تسوية بنكية بمطابقة يدوية
- موظفون: بصمة WebAuthn، تقييد جغرافي (Geofencing)، صلاحيات (حضور فقط/كامل)، كشف مشاركة جهاز بين موظفين
- رواتب: حساب تناسبي بالحضور الفعلي، ساعات إضافية بمعدَّل مختلف لكل موظف، رصيد مرحّل بين الأشهر، تاريخ توظيف وإنهاء خدمة، تعديل يدوي لساعات يوم معيّن (بإدخال وقت الدخول/الخروج)
- تقرير خبير بالذكاء الاصطناعي (تحليل نصي شامل)، تقرير تكلفة العمالة مقابل الإيراد
- إشعارات دفع فورية حقيقية (تصل حتى لو التطبيق مغلق): تسجيل حضور/انصراف، بث يدوي من المالك/المدير العام، تنبيهات أمان
- لوحة مدير عام (Super Admin) تدير كل المنشآت (تفعيل/تجميد/أرشفة)
- دعم لغتين كامل (عربي RTL / إنجليزي)

## نصيحة عملية لخطة العمل

1. استخرج `computeAll` و`computeAttendancePayroll` وكل الدوال المساعدة الحسابية البحتة إلى ملف/وحدة مستقلة أولًا (لا تعتمد على React) — هذه أهم قطعة بالمشروع كله.
2. اكتب اختبارات وحدة (unit tests) لهذه الدوال بسيناريوهات حقيقية قبل لمس أي شيء آخر.
3. افصل كل "تبويب" (Tab) لملف مكوّن مستقل تدريجيًا، بدءًا بالأبسط (كالتقارير) وانتهاءً بالأعقد (الرواتب، الجرد).
4. لا تغيّر أي اسم عمود أو جدول بقاعدة البيانات بلا ترقية SQL مصاحبة ومُختبَرة.
5. بعد كل خطوة فصل، قارن السلوك الفعلي (نفس المدخلات → نفس المخرجات) قبل المتابعة للخطوة التالية.
